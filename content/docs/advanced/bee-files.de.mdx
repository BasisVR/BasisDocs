Eine `.bee`-Datei (Basis Encrypted Experience) ist die einzelne Datei, als die jede Welt, jedes Prop und jeder Avatar ausgeliefert wird. Sie enthält eine Beschreibung des Inhalts sowie einen Unity-Build pro Plattform, alles verschlüsselt mit dem Passwort, das Sie beim Bauen festlegen.

## Aufbau

```
┌──────────────────────────────┐
│ Header: connector length     │  8 bytes, little endian Int64
├──────────────────────────────┤
│ Connector (encrypted JSON)   │  metadata, sections table
├──────────────────────────────┤
│ Section 1 (encrypted)        │  e.g. StandaloneWindows64
├──────────────────────────────┤
│ Section 2 (encrypted)        │  e.g. Android
├──────────────────────────────┤
│ ...                          │
└──────────────────────────────┘
```

Die Sections folgen direkt hintereinander auf den Connector, in der Reihenfolge, in der der Connector sie auflistet. Der Connector speichert die Länge jeder Section. Daraus lässt sich ermitteln, wo jede Section beginnt, ohne die Datei zu durchsuchen.

## Der Connector

Der Connector ist ein JSON-Dokument (`BasisBundleConnector`), das den Inhalt beschreibt, ohne ihn zu laden:

| Feld | Inhalt |
| --- | --- |
| `UniqueVersion` | Eine Build-ID. Ändert sich bei jedem Build. |
| `BasisBundleDescription` | Name, Beschreibung, Tags, Inhaltsgruppe und Urheberschaft (Autor, Kontakt, Lizenz, Credits). |
| `BasisBundleGenerated[]` | Ein Eintrag pro Section: Plattform, Asset-Modus, Asset-Name, CRC, Hash, Länge und Grafik-APIs. |
| `ImageBase64` | Das Vorschaubild, das in Menüs und auf Content-Orbs angezeigt wird. |
| `FarLodBase64` | Nur Avatare: ein winziger Platzhalter, der auf große Entfernung gezeichnet wird. |
| `DateOfCreation` | Build-Zeitpunkt (UTC). |
| `Bounds` | Die Größe des Inhalts, mit der er platziert wird, bevor er geladen ist. |
| `MetaData` | Anzahl von Dreiecken, Materialien und Bones, Texturspeicher, Render-Pipeline, Inhaltsart (Avatar, Prop oder Scene), Spawn-Platzierung für Props und eine Anzahl jedes Komponententyps. |

Da der Connector klein ist und zuerst kommt, können Menüs Namen, Vorschaubilder und Performance-Statistiken anzeigen, nachdem nur die ersten paar Kilobyte heruntergeladen wurden.

## Sections

Jeder `BasisBundleGenerated`-Eintrag beschreibt eine Section:

| Feld | Bedeutung |
| --- | --- |
| `Platform` | Das Build-Ziel, etwa `StandaloneWindows64` oder `Android`. `Generic` kennzeichnet den glTF-Fallback. |
| `AssetMode` | `Scene` für Welten, `GameObject` für Avatare und Props, `GLTF` für den generischen Fallback. |
| `AssetToLoadName` | Die Szene oder das Prefab, das aus dem Bundle geöffnet wird. |
| `AssetBundleCRC`, `AssetBundleHash` | Integritätsprüfungen für das entschlüsselte Unity-Bundle. |
| `EndByte` | Die Länge der Section in der Datei. |
| `AssetBundleEndByte` | Wo das Unity-Bundle innerhalb der entschlüsselten Section endet, wenn danach zusätzliche Daten folgen. |
| `GraphicsStatePayloads` | Offsets eingebetteter Shader-Prewarm-Daten pro Grafik-API und Qualitätsstufe. |

Eine entschlüsselte Section ist ein Unity-**AssetBundle**, optional gefolgt von **Graphics-State**-Daten, mit denen Shader vorgewärmt werden, damit der Inhalt beim ersten Anblick nicht ruckelt.

Die **Generic**-Section gibt es nur für Avatare: eine verschlüsselte `.glb` (glTF 2.0 binär) plus Avatar-Setup-Daten. Ein Client greift nur darauf zurück, wenn die Datei keine Section für seine Plattform hat. So erscheint ein Avatar auch auf Plattformen, für die er nie gebaut wurde.

## Verschlüsselung

Der Connector und jede Section werden separat mit dem Inhaltspasswort verschlüsselt:

- Chiffre: AES mit einem 256-Bit-Schlüssel.
- Schlüssel: aus dem Passwort mit PBKDF2 (SHA-1, 10.000 Iterationen) und einem zufälligen 16-Byte-Salt abgeleitet.
- Aufbau jedes verschlüsselten Blocks: `salt (16 bytes) | IV (16 bytes) | ciphertext`.

Sections über ein paar Megabyte werden in parallelen Blöcken entschlüsselt. Eine entschlüsselte Section kann höchstens etwa 2 GB groß sein; die Datei als Ganzes hat keine solche Grenze, weil immer nur eine Section entschlüsselt wird.

<Callout type="warn">
Das Passwort schützt Inhalte vor beiläufigem Kopieren und lässt Sie steuern, wer sie laden kann. Jeder mit der URL und dem Passwort kann sie entschlüsseln. Legen Sie keine Geheimnisse in Inhalte.
</Callout>

## Wie ein Client eine BEE lädt

1. Die ersten 8 Bytes (den Header) mit einer HTTP-Range-Anfrage lesen.
2. Den Connector herunterladen und entschlüsseln. Menüs können jetzt Name, Vorschaubild und Statistiken anzeigen.
3. In der Section-Tabelle die Section für diese Plattform suchen und ihren Bytebereich aus den Längen ermitteln.
4. Nur diese Section mit einer Range-Anfrage herunterladen. Sections anderer Plattformen verlassen nie den Server.
5. Entschlüsseln, die CRC prüfen und das AssetBundle laden (oder den Avatar aus glTF aufbauen).
6. Die Datei lokal zwischenspeichern. Beim nächsten Mal prüft der Client nur, ob sich der Inhalt geändert hat.

Deshalb kann eine `.bee` Windows-, Linux- und Android-Builds enthalten, ohne dass Quest-Spieler die Downloadgröße des PC-Builds tragen müssen.

## Hosting

- Jeder statische Host, der **HTTP-Range-Anfragen** unterstützt, funktioniert.
- Laden Sie die `.bee` hoch und teilen Sie ihre URL und ihr Passwort. Mit dem Passwort entsperren Spieler oder Ihre Load-Config die Datei.
- Ein Neubau erzeugt eine neue `UniqueVersion`, wodurch Clients Builds unterscheiden können. Clients gleichen zwischengespeicherte Kopien erneut mit dem Host ab. Wenn Sie die Datei unter derselben URL ersetzen, wird sie für alle aktualisiert.
