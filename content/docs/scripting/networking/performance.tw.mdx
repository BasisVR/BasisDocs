## 保持低成本

- 傳送狀態，而非每一幀。同步變數只在數值變更時傳送。不要從 `Update` 呼叫 `SendCustomNetworkEvent`。
- 使用最小的類型。用 `Byte` 或 `Bool` 取代 `Int`，用範圍浮點數取代原始浮點數。
- 高頻率資料使用不可靠傳遞。可靠訊息會重傳直到抵達為止，成本更高，且在封包遺失時會增加延遲。
- 保持 `DistanceReduction` 開啟。遠方的玩家會收到較少的更新。對於房間外沒人需要看到的物件，請開啟 `RelevanceCulling`。
- 一個物件，多個數值。一個含有十個數值的 `BasisSyncedParameters`，比十個各含一個數值的物件更便宜，因為每個物件都帶有自己的標頭和關鍵影格。
- 批次處理事件。將多個變更打包成一則訊息，而不是每次變更都傳送一則訊息。

<Callout type="info">
閒置的同步物件幾乎沒有成本：數值未變更時不會傳送任何東西，而關鍵影格的間隔會拉長。真正要避免的成本，是不需要卻每一幀都在變化的數值。
</Callout>

## 常見的同步錯誤

| 症狀 | 常見原因 |
| --- | --- |
| 您這邊正常，其他人都看不到 | 變更只在本機套用而從未傳送，或物件尚未網路就緒（`HasNetworkID` 為 false）。 |
| 晚加入者看到的是場景預設值 | 狀態是以事件傳送的，且沒有在 `OnPlayerJoined` 中重新傳送。請參閱[晚加入者](/tw/docs/scripting/networking/late-joiners)。 |
| 兩位玩家爭奪同一個數值 | 兩人都在寫入。只有擁有者應該寫入；請在玩家採取行動時取得擁有權。 |
| 數值在您變更後又跳回去 | 您在未擁有物件的情況下寫入同步變數，因此被擁有者的串流覆寫。 |
| 有人加入時一切都重設 | 在 `Start` 或 `OnNetworkReady` 中取得擁有權，導致新來者以預設值成為擁有者。 |
| 事件處理常式觸發兩次 | 在 `Start` 中訂閱後又在 `OnEnable` 中訂閱，或從未在 `OnDestroy` 中取消訂閱。 |

## 工具

- 播放模式中的檢查器。同步物件、拾取物和座位的檢查器會顯示擁有者、網路 ID、緩衝深度和每秒位元組數。
- 同步 gizmo。遠端同步物件會繪製它們先前的位置和正在前往的位置，即時顯示插值與外插的情況。
- 多個客戶端。建置一個客戶端並在編輯器旁執行，兩者都連線到本機伺服器。請參閱[測試](/tw/docs/world/testing)。
- `BasisStatsShim`（Cilbox）會回報往返時間以及距離上一個封包的秒數，適合用來顯示「重新連線中」的提示。
