## 保持低开销

- 发送状态，而不是逐帧发送。同步变量只在值变化时发送。不要在 `Update` 中调用 `SendCustomNetworkEvent`。
- 使用最小的类型。用 `Byte` 或 `Bool` 代替 `Int`，用范围浮点数代替原始浮点数。
- 高频数据使用不可靠传输。可靠消息会重发直到送达，这会带来更高的开销，并在丢包时增加延迟。
- 保持 `DistanceReduction` 开启。远处的玩家会收到更少的更新。对于房间外无人需要看到的物体，请开启 `RelevanceCulling`。
- 一个对象，多个值。一个包含十个值的 `BasisSyncedParameters` 比十个各含一个值的对象开销更低，因为每个对象都有自己的头部和关键帧。
- 批量发送事件。将多个变化打包进一条消息，而不是每次变化发送一条消息。

<Callout type="info">
空闲的同步对象几乎没有开销：值未改变时不发送任何内容，关键帧频率也会降低。需要避免的开销是那些本不需要却每帧都在变化的值。
</Callout>

## 常见同步错误

| 症状 | 常见原因 |
| --- | --- |
| 对您有效，其他人都看不到 | 变化只在本地应用而从未发送，或者对象尚未网络就绪（`HasNetworkID` 为 false）。 |
| 后加入者看到的是场景默认值 | 状态以事件形式发送，但没有在 `OnPlayerJoined` 中重新发送。参见[后加入者](/cn/docs/scripting/networking/late-joiners)。 |
| 两位玩家争夺同一个值 | 双方都在写入。只有所有者应当写入；在玩家采取行动时获取所有权。 |
| 修改后值又跳回原样 | 您在未拥有对象的情况下写入了同步变量，因此所有者的数据流覆盖了它。 |
| 有人加入时一切都被重置 | 在 `Start` 或 `OnNetworkReady` 中获取了所有权，因此新来者以默认值成为了所有者。 |
| 事件处理程序触发两次 | 在 `Start` 中订阅后又在 `OnEnable` 中再次订阅，或者从未在 `OnDestroy` 中取消订阅。 |

## 工具

- 播放模式下的检查器。同步对象、拾取物和座位的检查器会显示所有者、网络 ID、缓冲深度和每秒字节数。
- 同步 Gizmo。远程同步对象会绘制出它们曾经所在的位置和正在前往的位置，实时显示插值和外推情况。
- 多个客户端。构建一个客户端，与编辑器并排运行，两者都连接到本地服务器。参见[测试](/cn/docs/world/testing)。
- `BasisStatsShim`（Cilbox）会报告往返时间以及距上一个数据包的秒数，可用于显示“正在重新连接”提示。
